# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Development workflow

Code changes that involve a real judgment call — a new feature, a behavior change, anything with more than one reasonable way to build it — go through the superpowers workflow: `superpowers:brainstorming` to design it (propose approaches, ask clarifying questions, get explicit sign-off), `superpowers:writing-plans` to turn the approved design into a task-by-task implementation plan, then `superpowers:subagent-driven-development` to execute it with a fresh subagent per task, a task-scoped review after each, and a final whole-branch review before merge. Don't skip straight to editing files for these.

Trivial, mechanical changes with no design decision to make — a version-pin bump, a typo fix, a one-line config value change, updating a comment to match code that already changed — can be edited directly: make the change, verify with `npm run typecheck`/`npm run build`/`npm run lint`, and commit normally. If it's not obvious which category a change falls into, err toward the full pipeline. Documentation-only edits (README, this file) and pure investigation/analysis never need the full pipeline either way.

Any UI/UX update or decision — new markup, layout changes, styling, copy, interaction design — goes through the `impeccable` skill, which replaced `frontend-design` here once this project's design system was written down. Match the command to the size of the change: a new surface, or anything that would alter the visual world itself, invokes plain `/impeccable` (it routes through its own new-work flow); a bounded change invokes the scoped command that owns it — `layout`, `polish`, `clarify`, `adapt`, `harden`, `critique`, `audit`. A literal typo in a string is still just a typo fix. This is orthogonal to the superpowers pipeline above: a UI change with a real judgment call gets both — impeccable decides what it should look like, superpowers decides how the work is planned and executed — and a UI change too small for that pipeline still gets impeccable.

When that UI decision has more than one reasonable answer, the answer is a rendered comparison, not a written recommendation — and the procedure for producing one is the project skill `.claude/skills/comparing-design-variants/`: a Mobbin reference row, four named variants, and the current implementation as a labelled control, all in real `DESIGN.md` tokens with the real seed sites, published as an Artifact. It slots into impeccable's direction-exploration stage rather than competing with it; `DESIGN.md` stays normative throughout. The skill auto-matches, and `.claude/hooks/design-variants-reminder.sh` (a `UserPromptSubmit` hook in `.claude/settings.json`) injects a reminder on design-shaped prompts so it does not depend on that match — the workflow lived in auto-memory for a while, which is advisory context and therefore kept not happening. Keep the procedure in the skill and not duplicated here, for the same reason the sidecar's rule bodies are derived rather than copied.

Why the skill changed: `frontend-design` is built for establishing an identity that does not exist yet — invent a palette, pair display and body faces, pick a signature element, take an aesthetic risk. That is the wrong instruction set for this repo now. `PRODUCT.md` records durable product truth (one desktop operator; a rare, irreversible mutation and a quick "which hop broke" read, weighted equally; what is deliberately outside the app's scope). `DESIGN.md` records the committed visual system — North Star "The Warm Terminal", Ember on Hearth, the absolute mono-for-machine-facts / sans-for-sentences split, three status tones with `starting` and `unknown` deliberately neutral, and a set of named rules — with its sidecar, `.impeccable/design.json`, carrying what that file's frontmatter schema cannot hold (tonal ramps, shadows, motion, component snippets). Impeccable reads all of it at boot. Treat `DESIGN.md` as normative and extend it; do not reopen its decisions as part of an unrelated change.

Two upkeep obligations come with those files. `DESIGN.md` can lie: when a change adds or alters tokens or components, re-run `/impeccable document` afterward, before it starts citing rules the code no longer follows. Note that `document` will not silently overwrite an existing `DESIGN.md` — it stops and asks whether to refresh, overwrite, or merge, and a scoped refresh is usually right here, since this file's prose records decisions a full re-derivation would rewrite in its own words.

The sidecar drifts separately, and silently. Its `narrative.rules` holds a **second, independent copy of every named rule's prose**, so hand-amending `DESIGN.md` desyncs it with nothing failing — no test, no detector, no build. It drifted in six places across two changes before anyone checked, once in a review fix wave that amended `DESIGN.md` and recreated the defect it was closing. The bodies are now *derived* from the prose by one transform (strip `**bold**` and backticks); keep them derived, because impeccable loads both files at boot and a stale sidecar feeds a retired rule into the next design change. That extraction runs from a rule's bolded header to the next rule header or heading, not to the first blank line, which would truncate a multi-paragraph rule.

The design-detector hook **fires again, as of 2026-10-08** — on edits made in the main session and on edits made by subagents, both demonstrated by writing a throwaway `.ts` under `src/views` and watching `.impeccable/hook.cache.json` gain that session and file with a fresh modification time. **It only sees the Edit and Write tools** — its matcher is `Edit|Write` — so a view changed through a shell command (`sed`, a heredoc, a script) never reaches it. That is not hypothetical: the first UI change after the fix was made entirely through Bash, and the hook stayed silent while working correctly. Brief UI implementers to edit `src/views` and `public` with Edit/Write, and run the detector by hand whenever that cannot be guaranteed.

It had not fired from 2026-08-28 to 2026-10-08, and the cause was **outside the repo**. `impeccable` is installed with **project scope**, and Claude Code records a project-scoped install against the project's absolute path in `~/.claude/plugins/installed_plugins.json`. Ours named `~/WebstormProjects/lyly-admin` — where this repo lived before it moved under `personal/`. At the new path the plugin was not installed as far as the harness was concerned, so its `PostToolUse` and `Stop` hooks were never registered, while everything *in* the repo that a reader would check — `impeccable@impeccable` in `.claude/settings.json`, `hook.enabled`, consent in `.impeccable/config.local.json`, the plugin's `hooks.json`, `hook.mjs`, a recent Node — was present and correct. Invoked by hand with a synthetic edit event the hook worked at the new path; a real Write did not reach it. Re-installing the plugin from this directory (`/plugin`, project scope) added an install record for the new path, and the hook fired from the next edit, with no restart. The record for the old path is still there and harmless. **Moving this repo again will break the hook again**, silently, the same way: re-install the plugin from the new location, then demonstrate it.

That procedure has now been run deliberately once. On 2026-10-09 the folder moved from `personal/lyly-admin` to `personal/lychee-admin` along with the repository rename, and `impeccable`, `superpowers` and `playwright` were re-installed from the new path *before* any UI work — all three are project-scoped, so all three needed it, not just the one with a hook. The demonstration was the same as the first time: a throwaway Write to `src/views/`, then `.impeccable/hook.cache.json` showing a modification time from that minute and the new-path file under the current session's id. The Claude Code memory for this project is keyed to the absolute path too, so a move also means copying `~/.claude/projects/<old-path-key>/memory/` to the new key; nothing warns when it is missed, and the next session simply starts without it.

The manual run is still the cross-check when a change matters, and the only option if the hook is ever found not firing: `<impeccable-skill-dir>/scripts/impeccable detect --json src/views` (impeccable 4.5 replaced the old `node …/scripts/detect.mjs` with this launcher), which is cheap. Scope it to `src/views`, not `src public`: `public/style.css` is gitignored Tailwind output, and pointing the detector at generated CSS produces findings that exist in no source file — a stale-looking `border-radius: 1px` from inside a `calc()`, `#000` from Tailwind's own `color-mix()` fallbacks — which read as drift and are not.

These paragraphs have been wrong before, in both directions, and the way they were wrong is the point. They once claimed the hook *was* active and instructed the reader to disbelieve impeccable's own `MANUAL_DETECTOR_REQUIRED` directive; on 2026-10-02 the directive was right and this file was not. They then named two candidate causes, the repo move and subagent edits, without being able to tell them apart; the move was the cause — through the install record, not through anything in the repo — and subagents never were. The 2026-10-02 error cost a manual detector run to discover, and that run found a real off-ramp font size. **A tool reporting on its own state outranks prose asserting that state, unless the prose carries evidence newer than the report.**

The check that distinguishes them: the cache file's **modification time**, never its existence. A cache that exists but has not been written this session is indistinguishable from one written months ago, which is exactly the trap. `/impeccable hooks status` is the other reading.

## Purpose

`lyly-admin` is a small local web app that runs on a host named `lychee` (Ubuntu Server) and automates adding/removing subdomains for an existing Caddy + Cloudflare Tunnel setup. It replaces manually editing the Caddyfile and tunnel ingress config by hand.

**The repository is `LycheeHome/lychee-admin`; the app is still `lyly-admin`.** The repo was renamed on 2026-10-09 to match `lychee-ops`, `lychee-resources` and the `lychee-sites` tunnel — `lychee-` plus what the thing does, named for the host rather than a domain, since naming it for `lyly.dev` is what made the old name go stale. Only the repository moved. Everything the app *is* on the host — the `lyly-admin` user, `lyly-admin.service`, `/opt/lyly-admin`, `/var/lib/lyly-admin`, `/etc/lyly-admin`, `/var/log/lyly-admin`, the sudoers drop-in and the `lyly-admin-*` wrappers it pins — keeps its name, as does the `package.json` name, because renaming those is a host migration with ownership, sudo and unit changes under a live reconciler, not part of a repo rename. So throughout this file, `lyly-admin` means the app and its host identity, never a repository to clone.

**Tier 1 scope**: this app does not touch Cloudflare DNS. Creating a hostname's DNS record stays a manual, deliberate step (a proxied CNAME in the Cloudflare dashboard, or `cloudflared tunnel route dns` from a machine that has a Cloudflare login). The app only manages the local side: Caddy config, tunnel ingress config, `/var/www` directories, and service reloads/restarts.

## Stack

- Frontend: server-rendered HTML/vanilla JS — no frontend framework, this is a single-purpose internal tool. `src/views/` is three files: `shell.ts` (everything every page shares — the `<head>`, a header band aligned to the same 1080px container as the content, the flash toast, the copy-status live region, and the server-rendered page notice), `html.ts` (the page bodies: list, add, detail, not-found — including the site detail page's hostname-switcher dropdown, per-site navigation rather than page frame), and `shared.ts` (`escapeHtml`, the icon set, and the Tailwind class constants the other two both use). The old rail is gone, so the content box is the viewport again and `sm` (640px) means what it says — `html.ts` page bodies remain free to use responsive variants where it helps (e.g. the detail page's step arrows and metadata grid).
- Auth: Basic auth, single user, bcrypt-hashed password stored in `.env` or a local config file (never plaintext)
- Process management: runs as its own systemd service on `lychee`
- Entry points: `src/server.ts` (production — real system access) and `src/dev/server.ts` (local development — in-memory fakes). Both build a `Deps` object and hand it to `createApp` in `src/app.ts`. `src/dev/` and every `*.test.ts` are excluded from `tsconfig.build.json` and from the deploy rsync, so neither reaches `dist/` or `lychee`. There is no mock-mode environment flag: mock behavior is unreachable from the production entry point because it never imports the fakes.

## Running and testing locally

`npm run dev:mock` runs the whole app off-host — macOS or Windows — against
`src/dev/fakes.ts`, which supplies an in-memory filesystem and stubbed
privileged commands. It needs no `.env` (dev credentials are `dev`/`dev`,
set in `src/dev/env.ts`) and touches nothing on the machine. Seeded site
data lives in `src/dev/seed.ts` and covers every branch the Caddyfile parser
has, including one deliberately unmanaged `lychee.local` block that must
never appear in the site list. State is in memory only, so it resets on
every restart — including the automatic restarts `tsx watch` performs when
you edit a view.

`npm test` runs `tsx --test` (no new dependency — Node's built-in runner,
driven through `tsx` so the codebase's extensionless imports resolve). The
suite covers the four pure modules plus the add/remove/rollback route flows
against the fakes. Helpers shared between test files live in
`src/dev/testHelpers.ts` — in `src/dev/` because that directory is already
excluded from the build and the deploy rsync exactly as `*.test.ts` is, and
naming it `*.test.ts` would have had the runner collect a file with no tests
in it.

What local mode cannot tell you: sudoers scope, the wrapper scripts' own
validation, `web:webdeploy` ownership, and real `caddy validate` behavior
are all faked. Those remain verifiable only on `lychee`.

## Critical safety/security constraints

These are non-negotiable properties of the design — preserve them in any implementation:

- **Never expose this app through the Cloudflare Tunnel.** Bind Express to `127.0.0.1` or the LAN interface only. No tunnel ingress rule should ever point at this app's own port.
- **The app has a second, tailnet-only address: `https://admin.lychee.land`.** It is served by Caddy with a Let's Encrypt certificate, and the name resolves (a DNS-only A record made by hand) to `lychee`'s tailnet address, so only tailnet devices reach it; the address and the rest of the coordinates are in `lychee-ops`' `HOST.md`. `lychee-ops` owns all of it: its `admin_https` role keeps the site block in `/etc/caddy/conf.d/admin.caddy`, outside anything this app parses (the app reads only the `http://` blocks in the main Caddyfile, so the block can neither be listed nor removed from here), and asserts one `import` line in the Caddyfile. The role validates Caddy on every reconcile tick, so an invalid Caddyfile, including one this app wrote, fails the tick and alerts rather than waiting for the next restart to find it. It never touches the tunnel, so the rule above stands unchanged, and **`tailscale funnel` is never used for this app**: funnel is a public ingress by another name. The add-site reservation of `admin.lychee.land` exists now, as `RESERVED_HOSTNAMES` (see Environment this app manages): `hostnameExists` can only see the `http://` blocks this app parses, so it cannot know the HTTPS block in `conf.d` is there, and without the reservation add-site could be asked to create a block for the name this one is already serving. `lychee`'s `.env` must carry it, and `lychee-ops`' deploy gate refuses to install a build whose `.env` lacks it. The reasoning is in `docs/superpowers/specs/2026-10-09-admin-https-design.md`.
- **Never run the Express process as root.** It runs as the dedicated low-privilege `lyly-admin` user with narrowly scoped `sudo` rights, declared in `lychee-ops`' `sudoers.example` and reconciled onto the host. The grant is narrow and enumerated there — Caddy validate/reload/status, a `cloudflared-sites` restart, and three wrapper scripts, with the config-writing one pinned separately to each of the two files it may write. Read `sudoers.example` in that repo for the exact list rather than trusting a copy here; the whole point of it living there is that it is reconciled rather than believed. **`cloudflared-sites`, never `cloudflared`** — the latter is the now-retired `lychee-ssh` tunnel (see Environment this app manages). While it carried `ssh.lyly.dev`, granting it here would have let this app drop remote access to the host; with access on Tailscale the stakes are lower, but the rule is unchanged, because the grant buys this app nothing and would quietly re-create a dependency on a service meant to stay disabled. This bullet previously said the scope was three commands and named the wrong service; it was wrong on both counts for months, which is why the grant now lives in a file that is reconciled rather than in prose that is believed.
- **Always validate before reload.** Run `caddy validate --config /etc/caddy/Caddyfile` before every `systemctl reload caddy`. If validation fails, abort and surface the exact error — never reload a broken config.
- **Always back up before editing.** Copy the Caddyfile and tunnel `config.yml` to a timestamped backup (e.g. `/etc/caddy/Caddyfile.bak.<timestamp>`) before any mutation.
- **Fail closed, in order.** If any step in the add/remove flow fails, stop immediately, show the exact error, and do not proceed to later steps (e.g. don't reload Caddy if validation failed; don't restart cloudflared if the Caddyfile edit failed).
- **Never silently delete site files.** Removing `/var/www/<hostname>/` contents requires explicit user confirmation in the flow.
- **Log every mutating action** (what was added/removed, when) to a local log file for auditing.

## Environment this app manages

> Host coordinates — tunnel IDs, the tailnet address, uids and gids, and the exact
> sudoers command list — live in `lychee-ops`' `HOST.md`, which is private. This repo
> is public, and those identifiers have no value to a reader of it while collectively
> amounting to a map of the host's privilege model. What stays here is the reasoning:
> every decision, every failure that produced it, and every property the code must
> hold to. If a passage below reads as though a number is missing, it was moved, not
> lost.

- Domain: `lychee.land` (moved from `lyly.dev`; the old domain's sites and DNS records are not managed by this app any more). It is read from the **required** `DOMAIN` setting, which has no default anywhere in app code — a missing one stops the app at startup rather than guessing. All managed hostnames are subdomains, `*.lychee.land`, and validation matches the derived pattern in full. The same value drives the resource-name suffix (`-lychee-land`, `.` becoming `-`) and the longest Next.js label that fits a 63-character resource name; `lychee-ops` declares the same domain and its gate reads `DOMAIN` out of `/opt/lyly-admin/.env`, so the two cannot disagree silently. **`RESERVED_HOSTNAMES`** is optional and comma-separated (entries trimmed and lowercased, empty ones dropped); add-site refuses any hostname on it with `"<hostname>" is reserved`, in both the preview and the submit because both run the shared validator. On `lychee` it holds `admin.lychee.land`: see the second address in Critical safety/security constraints for why.
- Caddy config lives at `/etc/caddy/Caddyfile`. Existing site blocks use explicit `http://` prefixes (Caddy defaults to binding 443 otherwise), and the Caddyfile has a global `auto_https off` since TLS terminates at Cloudflare's edge, not on `lychee`. New site blocks must follow this same `http://` pattern.
- `lychee` ran **two** Cloudflare Tunnels, split deliberately so lyly-admin's restarts could never interrupt SSH. One is now retired and that rationale no longer applies, but the split is kept rather than folded back together — the remaining tunnel keeps its own service and config, and that separation is still what makes restarting it uneventful:
  - `lychee-ssh`, config at `/etc/cloudflared/config.yml`, service `cloudflared.service`. Carried `ssh.lyly.dev` only. **Retired 2026-09-26.** Interactive SSH through `cloudflared access ssh` froze within about a minute of real typing — reproducibly, across two terminals and both client versions — while the LAN path and bulk output *through the same tunnel* were flawless (15 minutes, 900/900 one-second ticks; 10MB at ~54 Mbit/s). The mechanism was never established: the server side looked healthy throughout, with sshd reporting the connection `established` and its queues empty, so nothing on `lychee` was ever going to show it. Host access moved to Tailscale, which holds under the same usage. The service is disabled, the `ssh.lyly.dev` DNS record is deleted, and `/etc/cloudflared/config.yml` plus its credentials are deliberately left on disk: restoring the path is a dashboard CNAME to that tunnel's `cfargotunnel.com` target (its ID is in `lychee-ops`' `HOST.md`) plus `systemctl enable --now cloudflared`, which is worth knowing *before* it is needed, since `cloudflared tunnel route dns` wants a `cert.pem` that only exists transiently. **lyly-admin must still never touch this tunnel, its config, or its service** — and nothing should be built that depends on bringing it back.
  - `lychee-sites`, config at `/etc/cloudflared/sites-config.yml`, service `cloudflared-sites.service` (declared by `lychee-ops`, `TimeoutStopSec=10` so restarts don't hang ~90s the way the original service's default 90s stop timeout did). Carries every hostname lyly-admin manages. The apex `lyly.dev` had a proxied DNS record pointing at this tunnel, which nothing served, until it was deleted ahead of the move to `lychee.land`: it was the original hand-built site from the 2026-07-21 setup this app replaced, removed through lyly-admin on 2026-08-08, and the remove flow deliberately leaves DNS alone — so the record survived it, and requests for the apex fell through to the ingress catch-all and got a `404`. This is the one `src/lib/systemCommands.ts`'s `restartCloudflared()` restarts and `writeManagedConfig()`/`TUNNEL_CONFIG_PATH` edit. Its ID is read out of that config file's `tunnel:` key via `readTunnelId()` — there is no `TUNNEL_ID` environment variable, so the ID shown on a site's page and used in its DNS command cannot drift from the tunnel actually carrying the hostname. That read is deliberately defensive: an unreadable file degrades to Cloudflare-dashboard instructions rather than erroring the page, so whether a site's Manual steps shows a concrete `<tunnel-id>.cfargotunnel.com` CNAME target or only the generic dashboard instruction is how you tell on `lychee` that the app user can actually read it. The `route dns` command is deliberately the fallback there, not the instruction: it needs an account certificate, `cert.pem`, which exists on the host only during `cloudflared tunnel login` and is deleted afterwards, so run on `lychee` it fails with "Cannot determine default origin certificate path".
  - A stale copy at `/home/byron/.cloudflared/config.yml` from initial setup was deleted; `cert.pem`/credentials for both tunnels live transiently in `~/.cloudflared` only during `cloudflared tunnel login`/`create`, then get copied to `/etc/cloudflared/` and the home copy is deleted again. Both tunnels run as root (no `User=` in either unit file).
- **Host access is Tailscale**, not a public hostname, and there is no longer any publicly resolvable SSH endpoint for this machine. `lychee` sits on a personal tailnet with node key expiry **disabled** — a headless node whose key expires drops off the tailnet with no way to re-authenticate remotely, which is the one setting here that cannot be fixed from where you would need it. `ufw` is active and its default-deny drops decapsulated tailnet traffic, so `ufw allow in on tailscale0` is load-bearing: without it `tailscale ping` succeeds while TCP to port 22 times out, which reads like a Tailscale fault and is not one.
- `/etc/caddy/Caddyfile` and `/etc/cloudflared/sites-config.yml` are both root:root, mode 644, in root:root 755 directories — the dedicated low-privilege app user has no direct write access to either. Config edits go through `lychee-ops`' `lyly-admin-write-config.sh` (installed as `/usr/local/sbin/lyly-admin-write-config`, root:root, mode 0700), invoked via `sudo` with the target path pinned to one of exactly these two files in that repo's `sudoers.example`. `src/lib/systemCommands.ts`'s `writeManagedConfig()` pipes new file content to it over stdin; never write these files with plain `fs.writeFileSync`.
- Site files are served from `/var/www/<hostname>/`, owned by a dedicated non-login service user `web` (`-s /usr/sbin/nologin`).
- Shared group `webdeploy` gives read/write access to site directories. Its members are `web` — through its **primary** group, which is why `getent group webdeploy` does not list it — plus `lyly-admin` as a supplementary member. Two principals — `github-runner` was a third until it was deleted on 2026-09-28, and `caddy` a fourth until `lychee-ops` declared it out on 2026-10-08 — and the list is not housekeeping: `/opt/lyly-admin` is `2775 lyly-admin:webdeploy`, so this is exactly the set that can rewrite the app's `.env`, which is why the reconciler parses that file instead of sourcing it (see Deployment). New static site directories should be created with `web:webdeploy` ownership and `2775` permissions (setgid, so new files inherit the group). Caddy reads site files as **other**, not through the group: every directory and file under `/var/www` is world-readable, which is all a file server needs, and what the membership actually bought `caddy` was write on `/opt/lyly-admin` and read of its `.env` — the process terminating tunnel traffic could rewrite the app it fronts. The consequence to recognise: a static site whose deployed files are not `o+r` now returns `403`, and the fix is the file's mode, not putting `caddy` back.
- Other users on the box: `byron` (personal/admin), `steam` (Palworld server), and `swee` and `palsave-api` — each a `nologin` system account owning exactly one service. `github-runner` was deleted 2026-09-28 along with the runner it existed for; `webdeploy`'s membership is correspondingly one principal smaller.
- **Every supplementary group membership on the box is now one that something actually uses**, which was not true before 2026-10-08: `caddy` held `webdeploy` and reached for nothing in it (it keeps `www-data`, which its own package's postinst added and which owns nothing here), and before 2026-10-02 far less of it was. `steam` is in `palworld` only. `swee` is in `palworld` and `adm` — the second because it tails the game server's journal with `journalctl -u <unit> -f` and reads `/var/log/unattended-upgrades/` to explain why the server went down. `palsave-api` is in `palworld` only: it reads saves and no journals. `lyly-admin` is in `webdeploy` only. The contrast between `swee` and `steam` is the useful part — both held `adm`, only one reads a journal, and the test is not whether a membership looks dangerous but whether anything reaches for it. That is a `grep` of the service's own source, not a judgement call.
- **`steam` held blanket passwordless root until 2026-10-02, and three services shared the account.** While they did, every one of them had it — a Discord bot's `/update` command genuinely depended on it for two months, because stopping and starting the game server needed more than the narrow grant it was supposed to use. `swee` and `palsave-api` now have their own identities and their own pinned grants, and both of `steam`'s sudoers drop-ins are declared absent by `lychee-ops`. `steam`'s own memberships went the same way on the same day — `sudo` and `adm` both removed, leaving `palworld` — so it is now what a game-server account should be: owns its save tree, belongs to one group, escalates by no path at all.

  None of this ever applied to `lyly-admin`, which has had its own account and its own narrow grant from the start — but it is the same principle that bullet rests on, demonstrated the expensive way: a shared account launders privilege between everything that shares it, and the grant you audit is not the grant that gets used. Two details are worth keeping because both were asserted wrongly first. The grant was recorded as unused bootstrap residue; the journal showed two months of runtime calls, because the narrower grant it was supposed to use permitted `restart` and the caller needed `stop` and `start`. And the second drop-in was recorded as a CI runner's; reading the file showed it named `steam`. Both were one command away the whole time.
- Changing `cloudflared`'s ingress config requires a full restart (`systemctl restart cloudflared`), not a reload — reload does not pick up ingress changes.

## Core v1 feature flow

1. **List sites** — parse `/etc/caddy/Caddyfile` into site blocks (hostname, type: static/reverse-proxy, local path or port), and show a per-site status pill for reverse-proxy sites, computed concurrently (`Promise.all`) using the same canonical status vocabulary as the detail page. Static sites get no pill; a site with no status entry gets no pill.
2. **Add a site** — its own page at `GET /sites/new`, not a modal, so the header can link to it. (The list page also keeps its own primary Add-site button — same label, quiet in the header and ember on the page, because that button is the entire call to action when there are no sites.) The page runs the 1080px frame and splits into a form column and a what-gets-written panel; the panel is fed by `POST /sites/preview`, which calls the same `appendSite` / `addIngressRule` / validators the submit does and writes nothing. Validation lives in `src/lib/siteValidation.ts` and is shared by both routes deliberately — a preview that can accept what the submit rejects is worse than no preview. Hostname (validated as `*.<DOMAIN>`, so `*.lychee.land` today; refused outright if it is in `RESERVED_HOSTNAMES`) + type (static or reverse proxy w/ port). Reverse-proxy sites also get an optional framework picker (currently just "Next.js"); picking one makes the site a container resource built from its own repository (see Reverse-proxy sites below), and add-site itself writes nothing for it beyond the Caddy and tunnel wiring. Reverse-proxy ports are checked for conflicts first: rejected if another reverse-proxy site already uses that port, if a declaration in `lychee-resources` claims it (any state, `absent` included — a retired declaration keeps its port until it is pruned), or if it's a reserved port (`lyly-admin`'s own `PORT`, or Caddy's admin API on `2019`). The claimed ports are read from the app's local clone once per request and passed into the still-pure validator, by both `POST /sites` and `POST /sites/preview`, so the preview and the submit cannot disagree about them either; an unreadable clone degrades to no claims, because the declaration writer re-checks the port when Attach writes the file. On submit, in this order: back up configs → append Caddyfile block (framework, if any, recorded as a `# lyly-admin-framework: <value>` comment inside the block, plus a `# lyly-admin-healthcheck: <path>` comment alongside it for Next.js-scaffolded sites) → if static, create `/var/www/<hostname>/` (`web:webdeploy`, `2775`, via `lychee-ops`' `lyly-admin-create-site-dir.sh`) with a placeholder `index.html`; any reverse-proxy site, Next.js included, skips this step (reported as skipped, not as a step that never ran) — a Next.js scaffold belongs in the site's repository, and the container runs from an image, so nothing on the host would read a directory → append tunnel ingress rule to the `lychee-sites` tunnel's config (inserted before the catch-all `http_status:404` line, pointing at `service: http://localhost:80`) → `caddy validate` (abort on failure, no reload) → `systemctl reload caddy` → `systemctl restart cloudflared-sites` → navigate to `/sites/<hostname>?created=1`. There is no success banner listing follow-up commands any more: the new site's own page states the DNS step permanently in Manual steps — lead: add a proxied CNAME named for the site's subdomain label in the Cloudflare dashboard, with the copyable target `<tunnel-id>.cfargotunnel.com`; fallback: `cloudflared tunnel route dns <tunnel-id> <hostname>` from a machine with a Cloudflare login, since the host keeps no `cert.pem` — with the real ID read from the tunnel's own config at render time (a missing DNS record is permanent state, so it must not live in something that vanishes on reload), and the `?created=1` notice's only job is to explain the status pill it arrives beside — for a Next.js site, that it reads `not deployed` until a repository is attached and its first image deployed, and that the "From a repository" card has the steps.
3. **Remove a site** — the UI is a single confirm-remove modal that lists the four steps in the order they run (Caddyfile block → tunnel route → validate and reload Caddy → restart `cloudflared-sites`) and states that a failed step stops the ones after it; it includes an "also delete site files" checkbox showing the exact path — offered only where a directory actually exists, which the page checks rather than infers from the site's type: every static site whose directory exists, and a Next.js site only if it predates site resources and still has the `/var/www/<hostname>/` its old scaffold was written into. A Next.js site that is **attached** gets a fifth listed step, `<label>-lychee-land.yml set to state: absent`, with a line saying that this is the step that stops the container — the reconciler takes it down on its next run, within five minutes. Confirming does, in order: remove the Caddyfile block and matching ingress line → validate + reload Caddy → restart `cloudflared-sites` (`POST /sites/:hostname/delete`, returns JSON) → for an attached site, a second, separate POST to `/sites/:hostname/detach`, which commits `state: absent` to the declaration in `lychee-resources` → if the checkbox was checked, a further separate POST to `/sites/:hostname/delete-files` that performs the actual `rm -rf`. Each is a distinct request, never one atomic operation, and each runs only if the one before it succeeded — a failed Caddy/tunnel removal can never cascade into a retired container or deleted files, and files are never deleted while their container is still declared running. `/detach` looks for a declaration, not a Caddyfile block, because by the time it runs the block is gone and a retry has nothing else to find. `readDeclarations` distinguishes the two cases that matter here: it returns `null` when the local clone cannot be read (absent, unreadable, or a directory with no `.git`, which is what a failed re-clone leaves) and `[]` when the clone is readable and declares nothing. So `/detach` answers `404` ("No declaration named <name>.yml") only when the clone is readable and has no such declaration, and `502` ("Could not read the local lychee-resources clone…") when it cannot tell. Neither ever reads as success: the client treats any non-ok response as a failed step and offers Retry. If `/detach` fails, the dialog closes (a modal makes the toast beneath it inert) and the toast carries a Retry that re-posts it and then resumes the chain where it stopped. Retiring is not deleting: the declaration, its port claim and the site's system account all stay until the declaration is deliberately pruned — a separate act, from the app's **Prune old declaration** button (see Reverse-proxy sites) or by hand in `lychee-resources`. On a site whose declaration is retired, Attach stays enabled with a warning beside it naming the file, and Prune sits beneath the warning: the page's clone may be stale, so the writer's own fresh pull decides, and it refuses with that prune reason if the retired file is still there. The client then reminds the user to remove the DNS record manually.

Every page renders inside the same shell (`src/views/shell.ts`): a header band aligned to the same 1080px container as the content column beneath it — no background, no bottom rule. The header carries the `lyly.admin` wordmark as a home link at its documented Display size, then quiet mono links to **sites** (`/`), **services** (`/services`) and **add site** (`/sites/new`), in that order: the two "what exists here" pages sit adjacent and the one action goes last (the same reasoning is recorded in `shell.ts`'s comment). `/services` is the board of declared units — read from the reconciler's published inventory and joined to live `systemctl show` state, no privilege required — and degrades to an explanation rather than erroring when the inventory is missing or empty. A header item's destination never changes with location — that is why per-site navigation is not in it. `aria-current="page"` is still both the accessibility signal and the styling hook, via the arbitrary `aria-[current=page]:` variant, and its treatment is Chalk on Hairline with a 2px Ember Edge left rule — deliberately not the `proxy` pill's ember fill, so a nav item and a type pill never look alike.

Site-to-site movement is a `<details>` dropdown on the detail page's breadcrumb hostname (`src/views/html.ts`), listing every managed site with a `static`/`:<port>` hint. It does not status-check, for the same reason the old rail design never did: the dropdown renders on every detail page, so a dot per row would cost a TCP connect or a `docker compose ps` per site per page view. The list page **does** status-check now, which is the point of putting pills there instead: one page, N checks, on the page whose job is the five-second glance — reverse-proxy sites only, since static sites have nothing to poll. `/sites/:hostname` marks no header item current; the breadcrumb carries the location instead.

There are two banner elements, deliberately distinct. `#flash-banner` is the transient client toast (`showBanner`/`hideBanner` in `public/app.js`) — `fixed`, so "Removing blog.lychee.land…" is visible when it fires from the Remove button at the bottom of a long page. `#page-notice` is the server-rendered page-load notice (today only `?created=1`) — in flow at the top of the content column, because as a fixed toast it covered the breadcrumb and hostname of the page it had just landed on.

The site detail page states the request path as a four-hop chain (Cloudflare DNS → the sites tunnel (shown as `cloudflared-sites` over its config directory) → Caddy → the site's files or local port), annotated with values derived from `config` — hops 2–4 carry live state and hop 1 does not and must not. The tunnel and Caddy hops show their systemd unit's state (one unprivileged `readUnitStates` call for both units, run concurrently with the per-site check, degrading to a neutral `unknown` if the read fails); the last hop reports the site itself. Hop 1 is Cloudflare DNS, which the app never touches (Tier 1 scope), so an indicator there would be invented health. Status uses one canonical vocabulary shared by the header pill and the last hop (`running`, `unhealthy`, `starting`, `exited`, `restarting`, `paused`, `not deployed`, `awaiting image`, `failed`, `unknown`, and `responding` / `not responding` for plain proxies); `starting`, `awaiting image` and `unknown` are neutral, not red. `failed` is the bad-tone opposite of `awaiting image`: the reconciler tried to deploy the first tag and could not, so nothing is installed and nothing will change until the operator reads why and deploys a different tag. `awaiting image` is an attached site the reconciler has not yet deployed anything for — attached before its first tag was pushed, or before the reconciler has looked — which is the expected state between two steps, not a fault, and there is no container to ask about until a version is installed. Manual steps carries only what nothing on the page automates: the DNS record always (dashboard CNAME first, `route dns` as the fallback), plus — for static sites — replacing the placeholder `index.html` add-site wrote, which Caddy is already serving, so nothing otherwise prompts the user to notice what is live. A Next.js site's deploy story is the **"From a repository"** card, and it has two shapes. Until a version is installed it is a four-step numbered runbook, in the order things happen: (1) commit the three scaffold files — `Dockerfile`, `.dockerignore`, `.github/workflows/release.yml` — shown **in full**, each at full height with its own copy button, wrapping rather than scrolling sideways; (2) create the repository in `LycheeHome` and push `v0.1.0`, with the tag command copyable; (3) Attach; (4) Deploy. Steps 1 and 2 happen in GitHub and say so; 3 and 4 are this page's only writes. A step is marked done from evidence the page actually has — 1 and 2 once the reconciler has found a tag, 3 once a declaration or inventory entry exists — never from the operator's say-so. Attaching before the first push is fine and the card says so: Deploy simply has nothing to offer until an image exists. Step 4 states, rather than offers, a tag that is already requested and not yet applied, because a second write of the same tag would only race the first; a blocked run shows its gate string, in full, instead. A failed run shows a failure line: the tag it tried, the reconciler's `failed_step` (published in the inventory since lychee-ops added it, and simply absent from an older one), and `journalctl -u lyly-reconcile` as a copyable command, because a failed first deploy publishes an empty `gate` and the step is the only explanation the inventory carries. A newer tag is still offered beneath that line, as it is beneath a blocked run's gate: the reconciler retries the failing pin every tick, so publishing a fixed tag and deploying it from here is the way out, and the tag that failed is never offered again. (It used to offer nothing after a failure, which left a hand edit of `lychee-resources` as the only exit.) Once a version is installed the setup is history, and the card collapses to facts — `running`, `requested` while a pin is in flight, `repository` — plus the same failure line when a redeploy failed (the pill stays the container's own state, since the old version is still installed), the gate line and the offer. The offer is the services board's own offer line and `[data-deploy]` button (`renderOfferLine` and `offeredTag` are shared, so the two pages can never disagree about whether a tag is on offer), posting to the same `/services/:name/deploy`, which reads the tag from the inventory and never from the request. It sits in this card rather than the page header so Visit stays the header's one ember action. `buildCommand` and `runCommand` close the card in every state as detail rows rather than copyable boxes: they describe what the generated Dockerfile bakes in and runs inside the image, not commands to run on the host. When the container is in a bad state, `docker compose -p <label>-lychee-land logs` sits in the request-path card beside the hop reporting the failure — by compose project name, runnable from anywhere, because the reconciler runs the container and there is no site directory to `cd` into.

The card has been rewritten twice and both earlier versions are worth remembering. It first led with a generated GitHub Actions workflow whose two real steps rsynced source into `/var/www/<hostname>/` and ran compose *there*, so it only ever did anything on a runner that **is** `lychee`; it was deleted rather than repointed at `ubuntu-latest`, which would have rsynced into the ephemeral runner's own filesystem, built a container there, destroyed the runner and reported success (see the self-hosted runner, below). It then led with an operator-run `docker compose up -d --build`. That is gone too, because the container is now the reconciler's to run: the release workflow the scaffold emits today builds on GitHub's runners and pushes to `ghcr.io`, and nothing in it knows where the image runs — which is what makes it portable where the old workflow was not.

## Deployment

CI and deployment are two separate systems now, and they meet at exactly one thing: a commit SHA. `.github/workflows/ci.yml` has a single job, **`test`**, on `ubuntu-latest`, for every pull request against `main` and every push to `main`: `npm ci`, then `typecheck`, `lint`, `test`, and `build`. It runs off-host deliberately — those checks need only `npm`, so pull-request code never executes on `lychee`. Nothing in this repo deploys anything any more. `lychee` pulls.

**Why the `deploy` job had to go.** It ran on the self-hosted `github-runner` on `lychee`, and a self-hosted runner reachable from a public repo is a remote-code-execution path onto the host. The mechanism is not obvious and is worth stating plainly: for a `pull_request` event GitHub runs the workflow file *from the PR's head commit*, so a fork supplies its own workflow and therefore its own `runs-on:`. Nothing you write in the workflow on `main` constrains that, because the attacker's workflow is the one that runs. Hardening the job was never going to work; the job had to stop existing. Splitting the two halves — public CI on GitHub's runners, deployment initiated by the host — is what makes publishing this repo safe, and publishing it is what buys branch protection (below).

**The reconciler.** `lychee` runs `ansible-pull` against the private `LycheeHome/lychee-ops` on a systemd timer, `lyly-reconcile.timer`, every 5 minutes, with `ExecStart` wrapped in `flock -n -E 0` so a by-hand run and a timer tick can never work on the same install directory at once. Each tick does, in order: load host-local secrets from `/etc/lychee-ops/secrets.yml` → install its own units (the reconciler owns them, so changing the interval is a commit rather than an ssh session) → declare the six host files that used to live in `deploy/` → fetch this repo as root over SSH → **gate on this commit's `test` job being green** → if the SHA moved, sync and build as `lyly-admin`, rsync into `/opt/lyly-admin` excluding `.git`, `.env`, `node_modules`, `src/dev/` and `*.test.ts`, `npm ci --omit=dev`, restart the `lyly-admin` service and health-check it (still a `401` from `/`, still because that is proof Express bound its port *and* basic-auth middleware ran — `systemctl is-active` only proves systemd thinks the process exists) → write `/var/lib/lyly-admin/deploy-status.json`. A commit whose health check fails is remembered in `/opt/lyly-admin/.failed-sha` and abandoned after three attempts, rather than rebuilt and restarted every five minutes forever.

**The job name `test` is load-bearing.** The gate reads `GET /actions/runs?head_sha=…&status=completed`, then `GET /actions/runs/{id}/jobs`, and requires every job named exactly `test` to have concluded `success`. Renaming the job key — or adding a `name:` override, which *replaces* the name the API reports — breaks nothing loudly. It silently stops every deploy, and the status file then reads `job test concluded: missing`, which looks like CI never ran rather than like a rename. The gate matches a **job** name, not a check-run name; they coincide today only because this workflow's job and its check run are both called `test`.

**The gate's token needs `Actions: Read`, and specifically not `Checks`.** The original design used the obvious single call, `GET /commits/{sha}/check-runs`, and that took the first cutover attempt down on the real host: GitHub has **removed** the `Checks` permission from fine-grained PATs — searching "check" in the permission picker returns "No items available" — so the call returns 403 on every tick. 403 and not 404 is the tell: the token authenticates and can see the repo, it is refused this one endpoint. Two `Actions: Read` calls answer the same question, which is why the gate is two requests instead of one. When that token is re-minted, grant `Actions: Read` and nothing else; reaching for the permission the old instructions named reproduces the outage exactly. The token is temporary in any case — it exists only because this repo is private, and the Actions endpoints answer unauthenticated once it is public.

**Host setup is no longer prose here, because prose is not enforcement.** `lychee-ops` declares and continuously reconciles the six files that used to live in this repo's `deploy/`: `/etc/systemd/system/lyly-admin.service`, `/etc/systemd/system/cloudflared-sites.service`, `/etc/sudoers.d/lyly-admin` (installed through `validate: visudo -cf %s`, which refuses a syntactically broken file — though not a valid file with the wrong content in it), and the two root-owned `0700` wrappers `/usr/local/sbin/lyly-admin-write-config` and `lyly-admin-create-site-dir`. It also installs a third wrapper that never lived here, `lyly-admin-resource-status`, which reads a declared container's state by compose project name: the services board's container rows and an attached Next.js site's page both read through it, and without it they degrade to `{ state: "unknown" }` rather than failing the page. `lyly-admin-docker-status` is retired: it read a container out of `/var/www/<hostname>/`, nothing in the app has called it since site resources (2026-10-05), and `checkContainerStatus` was removed along with the last of its plumbing, so `lychee-ops` declares the wrapper absent on the host along with its sudoers line. The old "one-time host setup this assumes" list is gone: it was a list of things a human had to remember, and those are now declarations that self-correct within five minutes of drifting. `github-runner`'s old deploy grant is declared *absent* rather than merely deleted from this repo — `/etc/sudoers.d/lyly-admin-deploy` is removed on every run, because deleting the example file here would never have removed the drop-in already installed on the host. Two things genuinely remain manual, because the reconciler cannot bootstrap its own credentials:

- **`/opt/lyly-admin` and the `.env` inside it.** The directory (`2775`, `lyly-admin:webdeploy`) is not created by the reconciler, and `.env` is never written by anything automated — place it once, `chown lyly-admin:webdeploy`, `chmod 640`. The health check reads `HOST` and `PORT` out of it. Reads and parses: it used to `. .env` under `set -a` as root, which is shell *execution* of a file that every `webdeploy` member can rewrite, ten seconds after `npm ci --omit=dev` has already run lifecycle scripts as `lyly-admin` in that same directory. That was strictly worse than the Actions deploy it replaced, where a compromised runner only bought code execution as `lyly-admin`. The parsed values are also constrained to shapes that cannot carry a scheme, credentials or a host:port pair, so a rewritten `.env` cannot steer root's outbound GET.
- **Two read-only deploy keys, as root.** `/root/.ssh/id_lychee_ops` for the ops repo, `/root/.ssh/id_lyly_admin` for this one, plus a `Host github.com` block in `/root/.ssh/config` pointing at the first. Separate keys so either can be revoked alone; the `config` block because both repos clone from the same literal `git@github.com:` remote and SSH has no other way to tell them apart. The app-repo fetch passes its key explicitly, but `ansible-pull`'s own checkout of `lychee-ops` does not — whatever identity `github.com` resolves to there is the one it uses.

The `lyly-admin` user and the `webdeploy` group also predate all of this and are not declared yet; that belongs to a later slice.

**Builds run as `lyly-admin`, and that user has no home.** It was created without `-m`, so `$HOME` pointed at nothing — and `npm` wants a cache under it. The reconciler sets `npm_config_cache=/var/lib/lychee-ops/.npm` on every npm task so it never needs one. `/home/lyly-admin` has since been created by hand as belt-and-braces, but the mitigation is the environment variable, not the directory: do not drop it on the strength of the directory now existing. Builds run as that user and never as root for the same reason the Express process does not: `npm ci` executes dependency lifecycle scripts, and those must not have privilege.

**Observability, such as it is.** There is no run-history UI. Nothing renders a list of deploys anywhere, and nothing will until something is built to do it. What exists is `journalctl -u lyly-reconcile.service`, `systemctl list-timers lyly-reconcile.timer`, the status file `/var/lib/lyly-admin/deploy-status.json` (`last_run`, `target_commit`, `installed_commit`, `result` — one of `deployed`, `skipped`, `blocked`, `failed` — and `gate`, which names *why* nothing was installed), and a Discord webhook fired by the unit's `OnFailure=`. Two states look like success and are not:

- **A tick that loses the `flock` exits 0 with no output**, which is indistinguishable in `systemctl status` from a clean reconcile. The real liveness signal is the status file's `last_run`, which a skipped tick does not touch. The blind spot is bounded rather than permanent: `TimeoutStartSec=900` SIGKILLs a genuinely stuck run, and that exit does trip `OnFailure=`, so at most about three ticks can quietly no-op before the problem announces itself.
- **After three failed health checks for the same commit, the retry cap engages, the play *succeeds*, and the notifications stop** — while the service is still down. Three alerts and then silence is the designed behaviour, not a bug. Recovery is `sudo rm /opt/lyly-admin/.failed-sha` (remove it; do not truncate or hand-edit it), not a fourth alert. The bootstrap procedure, the by-hand `ansible-pull` invocation and the rest of the recovery notes live in `lychee-ops`' own README — leave them there rather than copying them here, for the same reason the sidecar's rule bodies are derived rather than duplicated. Note also that `installed_commit` means "the last commit that passed a health check", not "what is on disk": after a failed deploy the new code is already installed and running while that field still names the old SHA.

**Branch protection is on, and `main` is gated on `test`.** The ruleset
(`lyly-admin`, id 24148404, enforcement `active`) requires a pull request,
blocks deletion and non-fast-forward pushes, and requires the status check
named `test`. Approvals are set to zero, which is right for a single operator:
the gate is CI, not a second pair of eyes.

This paragraph has been wrong twice, in opposite directions, and the second
error is the instructive one. It first said protection was impossible. It then
said it was *possible but not yet configured*, and explained that going public
was what bought it — "`LycheeHome` is on GitHub Free, and a private repo there
gets neither branch protection nor rulesets — both APIs return 403". **The org
is on the Team plan, not Free.** Private repos here take rulesets and always
did: `lychee-ops` is private and has carried an active `main` ruleset since
2026-09-28. So the trade this file recorded — publish the repo in order to
afford protection — never existed, and it was cited as a reason for publishing.
Publishing `lyly-admin` was still right, because it removed the self-hosted
runner's exposure; it just did not buy what this paragraph claimed it bought.
Both errors came from reasoning about a billing plan nobody had checked, which
is one `gh api orgs/LycheeHome` away.

**The job name `test` now has two consumers, not one.** The reconciler's deploy
gate matches a job named exactly `test`, and so does this ruleset's required
status check. Renaming it, or adding a `name:` override that replaces the name
the API reports, now blocks every merge *and* silently stops every deploy. The
merge failure is loud and the deploy failure is not, so the first symptom is a
blocked PR and the second is a status file reading `job test concluded:
missing`.

What this does not change is where a *blocked deploy* surfaces. The reconciler
still refuses to install a commit whose `test` job is not green, independently
of GitHub, so a red commit leaves `lychee` serving the last healthy build by two
mechanisms rather than one. A blocked deploy still shows up in the status file's
`gate` string, not on the pull request.

One consequence of that gate follows from its construction and has not been observed yet, so it is recorded here to be recognisable rather than as something seen: CI runs share a per-ref concurrency group with `cancel-in-progress`, so two merges to `main` in quick succession cancel the first run, and a `cancelled` conclusion blocks that SHA — "every completed run must be green" makes no exception for a run that never finished. In practice the next tick has already moved to the newer commit, so the blocked SHA is simply never the target. The symptom to recognise is a commit that looks green in the UI and reports blocked here.

**The self-hosted runner is gone, retired 2026-09-28.** The service is stopped and uninstalled, `/home/github-runner/actions-runner` is deleted, and the org lists no runners. A fork pull request against any public repo in `LycheeHome` can no longer reach `lychee`, which is the exposure that motivated this entire change.

It was retired earlier than planned, because the reason to keep it turned out not to exist. This file previously said scaffolded Next.js sites depended on it — they never could. The runner was registered at the **organisation** level, and an org runner is reachable only by repos inside that org; `LycheeHome` holds four repos, and after `swee` migrated none of them had a workflow using it. A scaffolded site lives in someone else's repository and would need its own runner. So `frameworkScaffold.ts` emitting `runs-on: self-hosted` was a portability defect in generated output — it handed someone a workflow assuming a runner they do not have — and never was a dependency on this machine. **Fixed 2026-10-02 by deleting the workflow, not by changing the runner line**, because the rest of the file was no more portable than that line: see the Deploy card's description above for why `ubuntu-latest` would have been the worse repair. No scaffolded site existed when it was removed, and the workflow was never written to disk — `getScaffoldFiles` then wrote only the Dockerfile, compose file and `.dockerignore`; the workflow was rendered on the detail page to be copied. The scaffold has a workflow again since site resources (2026-10-05), but a different kind: `.github/workflows/release.yml` builds an image on `ubuntu-latest` and pushes it to `ghcr.io`, and nothing in it names the host. The test that guarded the deletion was narrowed to match — generated files may not name `self-hosted`, `lychee` or `docker-compose` — and a second test pins every job's runner to exactly `ubuntu-latest`. Worth remembering as a shape: "X depends on this" was asserted, carried through two specs, and gated a retirement, without anyone checking whether X could reach it.

The `github-runner` account went with it. It was dropped from `webdeploy` first — that group is exactly the set that can rewrite `/opt/lyly-admin/.env`, so it went from four principals to three — and then deleted once `find / -user github-runner` confirmed everything it owned lived inside its own home (about 1500 files, almost all npm cache from deploys that no longer happen). Checking that first is not ceremony: `userdel` does not touch files outside the home directory, and the next account created inherits the freed UID along with ownership of whatever was orphaned. This account had previously owned `/opt/lyly-admin/node_modules`, which is what made an earlier `npm ci --omit=dev` fail with `EACCES`.

**Port `8787` was double-bound on `lychee` until 2026-10-02, and the reason it mattered is worth keeping.** `lyly-admin` binds the LAN interface; a separate uvicorn service — `palsave-api`, the Palworld save-parser — bound `127.0.0.1:8787`. They coexisted because they bound different addresses, and nothing was ever broken by it. The hazard was in the health check: if `HOST` were set to loopback, or `.env` lost that line and the parse fell back to its documented default of `127.0.0.1`, the check would reach uvicorn, get a `404`, and report a failed deploy for a perfectly healthy app.

That service moved to `8788` when it was given its own Unix identity, so `lyly-admin` now holds `8787` alone. The hazard did not disappear with it — a loopback fallback still fails the health check, because nothing answers there. What went away is the *misdiagnosis*: a refused connection says "wrong address", while a `404` from a real server on the right port says "the app is broken". Being answered plausibly by the wrong service is what made it fail in the safe direction and diagnose terribly, and that combination is the part that generalises. (The adjacent hazard is guarded in code: add-site rejects `lyly-admin`'s own `PORT` as reserved, alongside Caddy's admin API.)

**The path gate is gone; its lesson is not.** The Actions deploy was path-gated — `.github/scripts/deploy-needed.sh` skipped it when every changed path was documentation or editor/agent config, so a docs merge did not restart the service. The pull model has no equivalent and does not want one: it installs whenever the SHA on `main` moves, so a docs-only merge now does rebuild and restart the service once, within five minutes. That is a fair price for retiring a predicate whose failure mode was invisible in the dangerous direction. Keep the reason it was fragile, though, because the predicate was only the occasion. Its skip list rested on an invariant — nothing matching it may be read by the app or by `npm run build` — and that invariant was silently false for months: Tailwind v4 auto-detects sources across the whole project minus gitignored paths, so `build:css` really was reading `docs/**.md` and compiling class strings out of planning documents into `public/style.css`, about 22% of the shipped bundle on `main` and 38% on a busy feature branch. Harmless in practice, since the swept-in utilities matched no rendered markup — but nobody chose it and nothing failed. `src/styles/tailwind.css` still pins its sources with `source(none)` plus explicit `@source` directives for `src` and `public`, and the comment there still explains why `public` is not optional (`app.js` adds classes at runtime via `classList`, and dropping it would remove them from the bundle with nothing failing at build or test time). The general form outlives the mechanism: an invariant about what a build reads is a property to re-check whenever a build step gains a new input, not a fact that stays true on its own.

**Running `gh` against this repo.** Two GitHub accounts are logged into `gh` on the development machine, and the globally active one has no access to `LycheeHome` — it fails with a 404 that reads like the repo does not exist rather than like an auth problem. Prefix the command with a token for the account that does, rather than switching accounts, since `gh auth switch` mutates global state the machine's other repositories depend on:

```
GH_TOKEN="$(gh auth token -u <the account with access>)" gh pr list
```

Git itself needs no help here, and the two things are independent: `origin` is SSH and that key already authenticates as `byroncustodio`, while commit authorship comes from a conditional include in `~/.gitconfig` keyed on the remote URL (`includeIf "hasconfig:remote.*.url:git@github.com:LycheeHome/**"`), so commits carry the matching identity with no per-repo `user.email` to forget on the next clone.

## Reverse-proxy sites

Choosing "reverse proxy" instead of "static" means `lyly-admin` only wires up Caddy/tunnel routing to `localhost:<port>` — it does not run, deploy, or supervise whatever's listening there, and never invokes Docker or any other process manager itself. For a plain reverse-proxy site you keep that process alive yourself (its own systemd unit, PM2, Docker, etc.), the same way the Palworld server and `swee` bot are managed independently of this app: run `next start` (or equivalent) on a local port, then add it here pointing at that port.

**A Next.js site is a container resource, and the reconciler runs it.** Picking the framework does not move the boundary above; it moves who is on the other side of it. Since 2026-10-05 the container is not the operator's to start — it is declared in the `LycheeHome/lychee-resources` repository and run by `lychee-ops`' reconciler under its own `<label>-lychee-land` system account, exactly as `palsave-api` is. `lyly-admin` never touches Docker for it: it writes **requests** into `lychee-resources` (git commits pushed with its own deploy key, from a clone at `/var/lib/lyly-admin/lychee-resources` — no sudo scope, no wrapper), and the reconciler acts on them on its next tick. What it writes is deliberately small, and each write is its own request:

- **Attach** (`POST /sites/:hostname/attach`) creates `<label>-lychee-land.yml` — `test.lychee.land` maps to `test-lychee-land` (`resourceNameFor` in `src/lib/siteResource.ts`) — with image `ghcr.io/lycheehome/<repo>` and **no tag**, and the site's port. The operator types only the repository name; the registry prefix is fixed because the reconciler accepts no other path, and the port is read from the site's own Caddyfile block, never from the request, so a declaration can only claim the port Caddy already proxies that hostname to. The writer refuses an existing file (naming the prune, when the existing one is retired), a port another declaration claims, and a port below 1024 (the reconciler's validator rejects those, and one rejected declaration freezes every resource on the host for that tick); the route refuses this app's own reserved ports, which the writer cannot know about.
- **Deploy** writes a tag into that `image:` line — the services board's existing path, `writeDeclarationTag`, which now also completes a tagless line. Tagless is the point: every deploy, the first included, is the same offer-and-Deploy path the board already had, with the tag read from what the reconciler itself published as available.
- **Change repository** (`POST /sites/:hostname/repository`, `changeSiteRepository`) rewrites the repository part of a **tagless** declaration's one `image:` line, as text, keeping the registry, any quotes, the trailing comment and every other line. It exists for one mistake: a typo at Attach leaves the site awaiting an image that will never exist, and nothing else in the app could correct it, because every other write is pinned to the tag or the state. It is offered in step 3 of the runbook only once the reconciler has run and found no tag — and the copy names both causes, an unpushed `v0.1.0` and a wrong name, because from here they are indistinguishable. Tagless is what makes it safe: with no tag the reconciler has no compose action, no render and no pull for that declaration, so nothing is running from the old repository and nothing changes hands but a name. A tag means Deploy has run and an image from that repository may be installed under this name, port and account, and repointing it would swap one app for another underneath them — so the writer refuses it after its own pull (`code: "tagged"`, a 409: "deployed images can't change repository; remove the site instead"), as well as a retired declaration, a missing file, a non-site name and anything but exactly one tagless `ghcr.io/lycheehome/` image line. "Tagless" is decided on the **parsed** value, not the line's text: the line is found by pattern, but the old file must parse to exactly `ghcr.io/lycheehome/<the repo the line shows>` and the rewritten one to the new image with every other field equal, because a quoted YAML escape (`"…/foo\x3a1.0"`) reads as tagless to a regex and as tagged to js-yaml and the reconciler, and a lexical check alone would repoint a deployed site and silently drop its tag. The name comes from the hostname and only `repo` is read from the request, so the write still cannot reach a declaration this app did not create or touch a port.
- **Remove** sets `state: absent` (see Core v1 feature flow, item 3). It never deletes the file: the declaration, its port claim and the site's account stay until it is pruned.
- **Prune** (`POST /resources/:name/prune`, `pruneSiteDeclaration`) deletes a retired declaration in one commit, `<name>: prune retired declaration`. It is the app's first delete write, so it is guarded on both sides. The app's guards: **site names only** (`<label>-lychee-land`; a hand-declared resource such as `palsave-api` is refused before anything is read); **already `state: absent`**, checked by the writer on the parsed file **after its fresh pull**, never from the page's possibly stale view; and **confirmed down**, from the reconciler's own inventory — no installed version and a last `result` of `deployed` (a completed `down`) or `awaiting-image` (never installed), otherwise `409` "the container hasn't been confirmed down yet; try after the next reconcile" and nothing is written. `awaiting-image` alone is not proof, because a running site that has never been deployed publishes it too: Deploy writes a tag, a reconcile starts bringing the container up, and until that tick finishes the inventory still shows the previous one's `awaiting-image`. So on that path the route passes `requireTagless`, and the writer also requires the declaration's **parsed image to be tagless after its pull**, refusing with `code: "tagged"` — mapped to the same `409` — and committing nothing. A tagless declaration can never have been brought up, and no writer in this app removes a tag, so that closes the race; the `deployed` path needs no such check. The UI is a secondary **Prune old declaration** button, no modal, in two places: under a site page's detached warning, and on a services-board row whose site declaration is `absent`. The board reads the clone once per GET for that; an unreadable clone shows no button anywhere. Deleting the file is only the app's half. `lychee-ops`' reconciler then removes the rendered project (`/etc/lychee-resources/<name>/`) and the status file (`/var/lib/lychee-resources/<name>/`) — only on proof that the last run was a completed down or never installed **and** `docker compose ps -a` lists nothing — and after that deletes the site's system account, again only on proof: no process under its uid, and a `find -xdev` over the root filesystem for its uid or gid, bounded by a 120-second timeout, that comes back empty, because a freed uid is handed to the next account `useradd` creates along with whatever the old one left behind. At most one account is attempted per tick, rotating among the candidates, so an account's deletion can lag a tick or two behind its directories. Any failed proof keeps the thing and reports it rather than guessing.

The reconciler's side, in brief, because the page's states mirror it: a tagless declaration gets no compose action, no render and no pull; it creates the site's account if absent, runs tag discovery against `ghcr.io`, and publishes `result: awaiting-image` with the newest tag as `available`. That entry is what turns the page's last hop to `awaiting image` and puts the tag on offer. A site's state is decided in one place, `resolveNextjsSite` in `src/routes/sites.ts`, from its declaration and its inventory entry, and the list's pill and the detail page both use it so they can never describe one site two ways. The declaration wins whenever it exists, because the inventory has no notion of `absent`; a declaration with no inventory entry yet is still attached (the reconciler has not ticked), so reloading after Attach never offers Attach again. An inventory entry with **no** declaration counts as attached only when the clone could not be read (`readDeclarations` returned `null`): the reconciler removes a pruned site's `status.json` only once it can prove the site is down (and a `lychee-ops` without that cleanup rule never removes it), so its entry can outlive the declaration, and trusting it over a readable clone would leave a pruned-and-re-added site showing `awaiting image` until the cleanup ran — or forever — with no Attach and a Remove that retires nothing. The clone is refreshed — the same `git pull --ff-only` (or re-clone) a write does, on the same serialized queue, bounded at about 5s and never throwing — by `refreshDeclarations` on the GETs of `/sites/new` and of a Next.js site's page, so a prune done by hand on GitHub shows without waiting for this app's next write. The services board does not refresh: it reads the clone as it stands to decide where Prune is offered, and the prune route's writer pulls before it decides anything. Deliberately not on `POST /sites/preview`, which runs per keystroke, nor on `POST /sites`, so the preview and the submit still read the same clone; nor on the list page, the five-second glance. Only an installed version means there is a container to ask, through `lychee-ops`' sudo-pinned `lyly-admin-resource-status` wrapper by compose project name. A site's `/var/www` directory is never consulted for status.

**The scaffold targets the site's repository, not the host.** `src/lib/frameworkScaffold.ts`'s `getScaffoldFiles` is a pure function returning `Dockerfile`, `.dockerignore` and `.github/workflows/release.yml`, and the site's page renders all three in full to be committed; add-site writes nothing to `/var/www` for a Next.js site. The release workflow fires on a `v*.*.*` tag, runs on `ubuntu-latest`, holds exactly `contents: read` and `packages: write`, uses no action but `actions/checkout`, and pushes `ghcr.io/<owner>/<repo>:X.Y.Z` — the tag without its `v`, because plain `X.Y.Z` is the only form the reconciler recognises — with an `org.opencontainers.image.source` label so the package inherits the repository's access instead of needing its own. Nothing in it knows where the image runs, which is what the self-hosted workflow it replaces got wrong (see Deployment). The repository has to live in `LycheeHome`, because `ghcr.io/lycheehome/` is the only registry path the reconciler accepts. The old `docker-compose.yml` is gone from the scaffold: the reconciler renders the site's compose project itself, under a site profile it controls, so a compose file in the repository would be one nobody reads.

The framework choice is persisted as a `# lyly-admin-framework: <value>` comment inside the site's Caddyfile block (Caddy ignores `#`-prefixed lines) so it survives restarts and shows on the site's card in the list, and rides along with the Caddyfile's existing backup/validate/reload/rollback handling for free — removing the site deletes the whole block, comment included. That comment is also what makes a site eligible for Attach at all: the route requires a managed reverse-proxy site with `framework: nextjs`.

When Next.js is selected, an additional optional "Healthcheck path" field (default `/`) controls the `HEALTHCHECK` instruction baked into the generated Dockerfile — Docker polls this HTTP path inside the container on a fixed 30s interval to decide if it's healthy, and that verdict reaches the page as `running · healthy` / `unhealthy`. It is recorded as a `# lyly-admin-healthcheck: <path>` comment beside the framework one and is fixed at creation time: changing it means removing and re-adding the site, the same as changing framework or port. Sites created before that field existed have no healthcheck comment, so their Dockerfile is rendered with the default.

Next.js sites created **before site resources** still have the `/var/www/<hostname>/` their old scaffold (Dockerfile, compose file, `.dockerignore`) was written into, and possibly an operator-started container running from it. Neither is read any more: such a site reads `not deployed` until it is attached, and its page shows the same runbook as a new one. Its directory still appears as a `files` row and as the remove dialog's delete-files checkbox, because the page checks for the directory rather than assuming it from the site's type — and deleting those files has never stopped a container that was started from them.
