# Site detail page

## Problem

Site cards on the list page are dense and getting denser (type badge, path/port,
now framework) with no room to show more — and there's real information users
want to see per-site that doesn't belong on a card: for Next.js-scaffolded
reverse-proxy sites, whether the app has actually been deployed yet, and what
build/run commands the generated Dockerfile uses.

## Goal

Clicking a site card navigates to a dedicated detail page
(`GET /sites/<hostname>`) showing full details for that one site: static
sites show their path; reverse-proxy sites show their port and, if set, the
framework, a live "is anything listening on this port" status check, and the
framework's build/run commands. The Remove action moves from the card to this
page — cards become plain links, no interactive form nested inside them
anymore.

## Design

### New route: `GET /sites/:hostname`

Looks up the hostname the same way `GET /` does (`caddyfile.parseSites` +
`isManagedHostname` filter). If not found among managed sites, renders a
minimal "Site not found" message with a link back to `/` — not a raw 404.

If found, renders via a new `renderSiteDetail(site, sitesRoot, respondingOnPort?)`
function in `src/views/html.ts`. For reverse-proxy sites, the route first does
a TCP check (see below) against `127.0.0.1:<port>` and passes the result in;
for static sites this check is skipped entirely (`respondingOnPort` is
`undefined`).

### Shared `filesPath` helper (DRY fix)

The "does this site have a files-deletion path, and what is it" computation
(static → target; reverse-proxy with a framework → `sitesRoot/hostname`; else
none) currently exists independently in two places — `src/routes/sites.ts`'s
`/delete` handler and `src/views/html.ts`'s card template. This feature needs
it a third time, for the detail page's delete-files section. Extract it into
one shared function, `computeFilesPath(site: Site, sitesRoot: string): string
| null`, in `src/lib/caddyfile.ts` (next to the `Site` type it operates on),
and have all three call sites use it instead of duplicating the ternary.

### TCP status check

New file `src/lib/portStatus.ts`:

```ts
import net from "node:net";

export function checkPortOpen(port: number, timeoutMs = 500): Promise<boolean> {
  return new Promise((resolve) => {
    const socket = net.connect({ host: "127.0.0.1", port });
    const finish = (result: boolean) => {
      socket.destroy();
      resolve(result);
    };
    socket.setTimeout(timeoutMs);
    socket.once("connect", () => finish(true));
    socket.once("timeout", () => finish(false));
    socket.once("error", () => finish(false)); // ECONNREFUSED etc. = nothing listening
  });
}
```

Runs once per page load (not cached, not polled) as part of building the
`GET /sites/:hostname` response for any reverse-proxy site (framework or
not — "is anything listening on this port" is generically useful, not
Next.js-specific, and costs nothing extra to extend). The `error` listener is
required, not optional: an unhandled `error` event on a raw `net.Socket`
crashes the process, so ECONNREFUSED/ECONNRESET must be caught here rather
than left to propagate. 500ms timeout is generous for a loopback connection
(real local connect/refuse is sub-10ms); this only matters if something is
badly hung, which is unlikely on `127.0.0.1`.

This proves *something* is listening, not that it's healthy — a container
that crashed immediately after binding, or (in principle) an unrelated
process on that port, would both read as "Responding." Accepted tradeoff:
lyly-admin already prevents two managed reverse-proxy sites from sharing a
port at add-time, so the "wrong process" case only applies to a manually
added, unmanaged listener — a rare edge case. A crashed-after-bind container
is transient and self-corrects to "Not responding" once the process actually
dies and releases the port. Real Docker-backed status (`docker compose ps`
via a new narrowly-scoped sudo rule) was considered and explicitly rejected
for now — this project has spent significant effort keeping lyly-admin's
privilege surface minimal, and the accuracy gain doesn't justify the first
expansion of it.

### `frameworkScaffold.ts` — expose build/run commands as data, not just template text

`Scaffold` gains two fields:

```ts
export interface Scaffold {
  dockerfile: string;
  compose: string;
  dockerignore: string;
  buildCommand: string;
  runCommand: string;
}
```

`NEXTJS_DOCKERFILE`'s builder-stage `RUN` line and runner-stage `CMD` line are
generated by interpolating `buildCommand`/`runCommand` into the template,
rather than being separate hardcoded strings that could drift from what the
detail page displays. For this pass both are fixed constants
(`"npm run build"` / `"npm start"`, matching `create-next-app`'s defaults) —
`getFrameworkScaffold`'s public signature doesn't change. This is purely an
internal restructuring so the two values have exactly one source of truth,
and so a future "let the user override these" feature (explicitly out of
scope here, but named as a likely next step) has an obvious seam: accept
optional overrides in `getFrameworkScaffold`, default to the current
constants when absent.

The detail page displays `buildCommand`/`runCommand` as two labeled code
snippets — not the raw Dockerfile. Nothing renders the Dockerfile/compose/
dockerignore content itself on this page.

### Site cards become plain links

`src/views/html.ts`'s card template: the `<form class="delete-form">`
wrapping a `.delete-trigger` button is removed entirely. The `<article>`
becomes an `<a href="/sites/<hostname>">` (same existing Tailwind classes,
element tag changed) wrapping the hostname, badge, and detail line exactly as
before. No JS click-handling needed for card navigation — it's a real anchor.

### Remove action moves to the detail page

The confirm-remove-dialog moves from the shared list-page markup into
`renderSiteDetail`'s output, and becomes site-specific rather than generic:
since the page is already scoped to exactly one site, the server renders the
checkbox/path text/Docker warning directly from that site's already-computed
`filesPath`/`framework`, with no client-side `data-site-path`/`data-framework`
attribute-toggling needed. The Remove button's click handler shrinks to just
`confirmRemoveDialog?.showModal()`.

The Remove button carries `data-hostname="<hostname>"` so the client JS knows
what to submit against without needing a form or page-global state (same
lightweight convention already used for `#port-owners-data`).

Confirming: dialog closes → `showBanner("Removing <hostname>…", "info")` →
`fetch` `POST /sites/<hostname>/delete` (unchanged endpoint/contract) → if
`needsFileConfirm`, immediately follow with `POST /sites/<hostname>/delete-files`
(same pattern as today) → on success, `window.location.href =
"/?removed=" + encodeURIComponent(hostname)`. On any failure,
`showBanner(errorMessage, "error")` and stay on the page (dialog is already
closed; the user can click Remove again to retry).

### List page picks up the post-delete banner client-side

No server changes needed for this. On every page load, `app.js` checks
`new URLSearchParams(location.search).get("removed")`; if present, calls
`showBanner(\`Removed ${value}.\`, "success")` and
`history.replaceState(null, "", "/")` to drop the query param so a refresh
doesn't re-show the banner.

### Net simplification to `app.js`

With deletion no longer happening in-place on the list page:
- `pendingDeleteForm`, `wireDeleteForms()`, and the `.delete-form`/
  `.delete-trigger` querying are deleted — there's no longer a delete form on
  any card.
- `removeCard()` (including its `portOwners`-pruning loop) is deleted —
  removal now always ends in a full navigation to `/`, which naturally gets a
  fresh, correct `portOwners` from the server's `#port-owners-data` script tag
  on that fresh load. No client-side pruning is needed.
- The confirm-remove-dialog's DOM refs and submit handler move conceptually
  from "generic, populated per-click" to "specific to the one site this page
  is for" — the handler still exists, just simpler (no per-click population
  step, hostname/checkbox state read directly since there's only ever one
  relevant site on the page).

`refreshSitesGrid()` and the add-site flow are untouched — adding a site
still happens via the modal on the list page, unrelated to this change.

### Page layout

Reuses the app's existing bordered-panel/pill/button vocabulary. No new
`layout()` variant — the detail page nests a `max-w-[640px]` column inside
the existing full-width `<main>`.

```
← Back to sites

blog.lyly.dev                                    [proxy]

┌─────────────────────────────────────────────┐
│ Local port: 3000                             │
│ Framework: Next.js                           │
│                                               │
│ ● Responding on localhost:3000               │
│   (or:)                                      │
│ ● Not responding on localhost:3000            │
│   Run docker compose up -d --build in         │
│   /var/www/blog.lyly.dev/ to deploy.          │
│                                               │
│ Build command                                │
│ npm run build                                │
│                                               │
│ Run command                                  │
│ npm start                                    │
└─────────────────────────────────────────────┘

[ Remove site ]
```

For static sites, the panel is just the path line — no status/commands
section. Build/run commands only render when a framework is present; the
status line renders for any reverse-proxy site regardless of framework.
Color-wise: rose for "Responding" (the app's existing positive/notice color;
there's no green anywhere in this palette), neutral stone for "Not
responding" (an expected pre-deploy state, not an error).

### Out of scope

- No polling/auto-refresh of the port status — checked once per page load.
- No Docker-backed status check (see TCP Status Check section above for why).
- No ability to customize build/run commands yet — `frameworkScaffold.ts`'s
  restructuring only sets up the seam for this, doesn't build the UI/
  persistence for it.
- No display of the raw Dockerfile/docker-compose.yml/.dockerignore content —
  only the extracted build/run commands.
